Case study

The gate that signed off 4,003 tables

Before a regulated migration can complete, someone has to prove the copy matches the original. Building a check trustworthy enough to carry that signature took two rounds of catching the check itself being wrong.

PostgreSQLCorrectnessToolingGo

To sign off a database migration you need to prove the copy matches the original. Row counts are not enough — they miss changed values entirely — so the check was a per-table fingerprint: an order-independent sum of a hash over every column of every row, which catches a single altered byte anywhere in the table.

Days before cutover it reported a mismatch on the general ledger: identical row counts, completely different fingerprints. The easy response is to believe the tool and go hunting for corruption. The useful one is to ask whether the tool is right.

It was not. The fingerprint hashed each row's *text rendering*, and how PostgreSQL renders a value depends on session settings. The source ran in one timezone, the containers in UTC. Every timestamp rendered differently, so byte-identical data produced entirely different hashes — reproduced deliberately on two servers differing only in that setting.

The fix pins the rendering settings — timezone, date style, interval style, float digits, byte output, monetary locale — identically on both connections, and reports each server's real settings separately so a mismatch is visible rather than silently absorbed.

The next run surfaced a table with *more* rows on the destination than the source. A replica cannot invent rows, so the source was still being written. That produced the second idea the gate needed: a table whose own fingerprint moves between two samples of the same side is classified as live, not as a mismatch — with a strict mode that turns those into hard failures once writes are quiesced for the real cutover.

Later, rebuilding this as a standalone Go tool, the question came up of whether sampling could make it faster. The research reversed the recommendation: the established tools in this space do not sample at all, and PostgreSQL's own TABLESAMPLE samples physical pages — on two servers with identical contents but different physical layout, the same seed returned different rows. So the tool hashes a logical key instead, and both sides select the same rows reproducibly. It also pushes its session settings in the connection startup packet and reads them back, refusing the connection if any did not apply.

With both corrections in place the gate did its job: 4,003 tables verified identical across the full staging rehearsal, and the same mechanism carried through the production cutover.

What it cost

Content comparison is expensive and there is no way around it: a one percent sample and a full scan touched the same 1,248,588 blocks, because the sampling predicate cannot use an index. The honest conclusion was that being both complete and faster than reading every row is impossible for content — only the key set can be verified at full coverage cheaply, via an index-only scan. The tool was built to be correct first and fast second, and says so.

Evidence

Shell gate used for the migration (three in-cluster variants); standalone Go rewrite with 18 injected schema mutations all detected, 23/23 subtests passing, verified across a PostgreSQL 14 to 16 pair
