Case study

Moving a bank's ledger, and proving it arrived intact

333 GB of regulated payments data moved onto Kubernetes overnight. The move was the easy part. The job was proving, before the country opened for business, that every cent had arrived.

PostgreSQLVM to KubernetesDC/DRRegulatedData Integrity

A central-bank-regulated payments platform, 333 GB across 17 databases, moving off self-managed PostgreSQL on VMs onto self-managed Kubernetes — a three-node synchronous cluster with a second datacenter for disaster recovery. The migration was physical, a base backup plus streaming replication, so the new cluster ran as a live replica of production for days beforehand. That is what keeps the outage short: cutover is the promotion of a replica that is already caught up, not a restore of 333 GB.

Before any data could move, the platform had to exist — and neither site did yet. Each was built from bare cloud VMs on Huawei Cloud: VPC and subnets, security groups, and VPN access for the engineering team, once for the primary datacenter and again for DR. Five VMs were provisioned per site; four formed a self-managed k3s cluster — three control-plane nodes carrying embedded etcd, plus a worker — and the fifth was held back for separate use. TopoLVM presented node-local LVM volumes so the database writes to disks physically attached to its own node rather than across a network. Backups to object storage and continuous write-ahead-log shipping for point-in-time recovery went in before the first byte of client data arrived.

The rehearsal came first. A full staging migration, then the content gate across every table — row counts plus an order-independent fingerprint over every column — until 4,003 tables verified identical against the source. Only then was a production date discussed.

Cutover went to plan. Writes were quiesced, the source's write-ahead-log position frozen and confirmed unchanged across two samples two seconds apart, replay confirmed caught up, and the new primary promoted. Both standbys re-attached within seventy seconds, synchronous replication intact. The old VMs stayed running as the rollback path — nothing is decommissioned on the night.

Then the part that decides whether a migration is finished. A database that starts is not a migration that worked; the data has to be shown to be right. The gate ran again against the live platform and the ledger tables came back identical — 22,463,214 rows and 493,889 rows, with monetary sums matching to six decimal places, and wallet balances summing identically on both sides. Not a cent had moved.

The same checks surfaced something the database layer never would have: a second copy of the application's background scheduler, still pointed at the old database through the rollback window. An application-tier detail, invisible to every database-level health check, found because the verification compared content rather than trusting that replication had done its job.

The platform opened on Kubernetes that morning, with the ledger proven and the rollback path still standing behind it.

What it cost

The clean 4,003-table figure is the rehearsal, where the source could be frozen. On the night the same checks ran against a source deliberately kept live for rollback, so they function as a health check rather than a pass/fail gate — forward drift on a running source reads as a difference by design. The claim that holds is the precise one: the ledger was proven identical, and everything else was identified and accounted for. Running the comparison early against a live source is exactly what exposed the second scheduler.

Evidence

Sanity-gate logs either side of cutover (501/507/504 pass, 12/6/9 fail on the main database; 239/238 pass, 8/9 fail on the core-banking database); ledger comparison captured during the incident
